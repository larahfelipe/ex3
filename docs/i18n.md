# Internationalization

The web renders in Brazilian Portuguese (`pt-BR`) by default and in American
English (`en-US`) when a person picks it. Every word it shows comes from a
message catalog. Every number, amount and date is written by `Intl` in the
interface's language. The API still answers in English: the web never shows
its text, and words each error from its own catalog.

## Locale

| Item | Value | Where |
| --- | --- | --- |
| Supported locales | `pt-BR`, `en-US` | `LOCALES`, `src/i18n/config.ts` |
| Names shown | `Português (Brasil)`, `English (United States)`; `Português`, `English` where the region does not fit | `LOCALE_NAMES`, `LOCALE_SHORT_NAMES` |
| Default | `pt-BR`, for a new visitor | `DEFAULT_LOCALE` |
| Fallback | anything unsupported (`en`, `pt-PT`, `en-us`, `''`, a stale value) reads as the default | `resolveLocale` |
| Preference | the `ex3:locale` cookie, `path=/`, one year, `samesite=lax` | `localeCookieOf`, `src/i18n/locale-cookie.ts` |
| Document language | `<html lang>` in the request's locale, updated in place on a switch | `app/layout.tsx`, `LocaleProvider` |
| Time zone for messages | `UTC` | `APP_TIME_ZONE` |

The locale is not negotiated from `Accept-Language`: a new visitor gets
`pt-BR` until they pick another language. The server reads the cookie once per
request (`getRequestLocale`, `src/i18n/server.ts`) and renders the page in
that language, so the server and the browser write every value the same way,
and hydration never sees two spellings of one date or amount.

## Choosing the language

`LanguageSelect` (`components/language-select.tsx`) offers every locale in
`LOCALES`, each named in its own words and marked with its `lang`, so a screen
reader pronounces it. It appears in two places:

* **The sidebar**, as an item of the bottom group, between the account and
  sign-out. On the rail it reads "Idioma" under its icon; expanded, it adds the
  short name. The list opens to its right. Like sign-out, it is left out of
  the mobile bar, which has no room for it.
* **The account page**, as the *Language* field of the *Preferences* section,
  on every screen size.

Both read and change the same state, `LocaleProvider`
(`providers/locale-provider.tsx`), through `useLocaleSwitch`, so they always
show the same language. A choice:

1. shows at once in both selectors, marked busy, while the other catalog
   loads. Each catalog is a chunk of its own (`messages/load.ts`), so the
   browser downloads only the one picked;
2. renders the whole tree again in place, in the new language: text, dates,
   numbers, amounts, the calendar's month and weekday names, and `<html
   lang>`. Nothing remounts, so typed values, open dialogs, filters, the
   address and the sidebar's state stay;
3. saves the cookie, then calls `router.refresh()`, so what the server
   rendered, such as the page title, follows.

The last choice wins: a catalog that arrives after a later one is dropped
(`runLocaleSwitch`, `src/i18n/switch-locale.ts`). A catalog that fails to
load leaves the language and the cookie as they were, and a toast says so.

A form's validation messages are written when a field is checked, so
`useRevalidateOnLocaleChange` checks again, in the new language, the fields of
the account, portfolio, transaction and Finances forms that show one. Fields
without an error stay unchecked, and errors the server set stay as they are.

## Library

[`use-intl`](https://next-intl.dev/docs/environments/core-library) 4, the core
of `next-intl` without its routing or middleware: the locale comes from a
cookie, not from the address, so URLs are the same in every language. It
provides:

* ICU MessageFormat: interpolation, `plural`, `select` and rich-text tags;
* keys and arguments type-checked against the default catalog, through the
  `AppConfig` augmentation in `src/i18n/app-config.d.ts`;
* `useTranslations` and `useLocale` for components, and `createTranslator`
  for everything else.

Two dev dependencies support the tests. `tsx` runs them. `intl-messageformat`
is the same version `use-intl` already bundles, and the catalog test uses it to
parse every message.

## Structure

```text
src/i18n/

  format.ts           formatOf(locale) and useFormat(): the formatters bound to a locale
  server.ts           getRequestLocale() and getServerTranslator(namespace)
  translator.ts       translatorOf(locale, namespace) and the Translator<Scope> type
  locale-cookie.ts    the preference cookie
  switch-locale.ts    runLocaleSwitch, the order of a switch's steps
  errors.ts           missing-key reporting and fallback
  rich-text.tsx       srOnly, the shared <hidden> tag
  messages/
    catalog.ts        Messages, typed from pt-BR; LocaleMessages checks a catalog's shape
    index.ts          MESSAGES by locale, for the server
    load.ts           loadMessages(locale), one chunk per catalog, for a switch
    en-US/index.ts    the same namespaces, translated
    pt-BR/index.ts    one namespace per file:
      common          actions, pagination, form chrome, states
      navigation      sidebar, page titles
      auth            sign-in, sign-up, password rules, sign-out
      account         profile, password, deletion
      investments     overview, assets, asset detail, charts
      portfolios      portfolio list and forms
      transactions    transaction types, form, list, toasts
      finances        categories, payment methods, statuses, kinds, history,
                      summary, charts, navigation, toasts
      financeOverview, bills, installments, recurring, calendar, reports
                      one per Finances screen
      validation      every form message
      errors          API, transport and category messages
```

`LocaleProvider`, inside `providers/app-provider.tsx`, renders `IntlProvider`
with the active catalog for client components. The root layout seeds it with
the request's locale and only that catalog. Server components and page
metadata use `getServerTranslator`, which reads the request's locale; tests
use `translatorOf(locale, namespace)`. Both read the same zone, catalog and
error handling as the provider.

## Using messages

```tsx
const t = useTranslations('bills.filters');
t('activeCount', { count });

const { formatMoney } = useFormat();
formatMoney(amount, currency);

const t = await getServerTranslator('navigation.pages');
```

* **A helper that writes text takes a `Translator<Scope>`.** Examples:
  `describeEvent`, `changeTextOf` and `apiErrorMessageOf`. The component passes
  its own `t`, so the helper stays testable and never reads a global.
* **A helper that writes a number or a date takes a `Format`.** The
  component passes `useFormat()`, as in `describeEvent(event, currency, t,
  format)` and `totalsText(totals, format)`.
* **Schemas are factories.** Examples: `positiveMoneyFieldFor(t)`,
  `emailSchemaFor(t)` and `reminderSettingsSchemaFor(t)`. A form builds its
  schema in `useMemo` from `useTranslations('validation')`, and from
  `useFormat()` when a message names an amount, so a switch rebuilds it.
* **Toasts are written by the web.** `useFinanceMutation` takes an
  `announcementOf(t, data, variables)` keyed in `finances.notifications`. The
  asset, transaction, portfolio and account hooks also word their toasts from
  the catalog. A response's `message` is never shown.
* **Enum values are keys.** For example, `finances.categories.FOOD` and
  `finances.statuses.OVERDUE` are keyed by the API's own value, so
  ``t(`statuses.${status}`)`` is checked against the union. The old
  `*_LABELS` tables in `common/constants.ts` are gone.

## Message conventions

* **Keys** are camelCase, grouped by screen or domain, and stable. A key names
  what the text is for, such as `paidOn` or `activeCount`, never its wording.
* **Numbers go through ICU** as `{count, number}`, so they are grouped:
  `1.234 contas`. A plain `{x}` is text.
* **Values arrive formatted.** A message takes amounts from `formatMoney` and
  days from `lib/dates`, never a raw `Date` or decimal.
* **Plurals.** Every `plural` has `other`. CLDR puts 0 in Portuguese's `one`
  category, so a count that can be zero needs an explicit `=0` branch:
  `{count, plural, =0 {Nenhuma conta} one {# conta} other {# contas}}`.
* **Context uses `select`.** For example, `summary.same` reads "Igual ao mês
  passado" or "Mesmo valor que em set. de 2026".
* **Rich text** uses tags, never markup concatenated in JSX:
  * `<hidden>…</hidden>` holds words for screen readers only. It is rendered
    with `srOnly`, as in `Estornar<hidden> o pagamento de {day}</hidden>`.
  * `<muted>…</muted>` holds secondary text in the same sentence, as in
    `optionalLabel` and `paidOn`.
  * An empty tag such as `<label></label>` or `<money></money>` places an
    element the component renders.
  * A tag's name must differ from every argument's name.
* **Spacing belongs to the message.** Never `{' '}` between JSX expressions.
  Prettier and `react/jsx-newline` fight over it, and a translation cannot
  move it. A message has no leading or trailing space, which the catalog test
  checks.
* **Apostrophes** are literal. An apostrophe before `{`, `}`, `#`, `|`, `<` or
  another apostrophe would start ICU quoting, and the test refuses it.
* **Not translated:** user data such as descriptions, names, notes and
  accounts; tickers and instrument names; institution names; currency codes;
  the language names, each written in its own language; and the product name,
  `APP_TITLE`.

`react/jsx-no-literals` (`noStrings`, props ignored) fails the lint on any text
written into JSX. Its allowlist is punctuation only: `· – — / : % ( ) + - ×`.

## Missing keys

A wrong key is a type error. A key built at run time that escapes the compiler
is reported, outside production, as
`[i18n] Missing message: <namespace.key> …` on the console. The interface then
shows the key's path instead of failing the page. The component tests'
provider throws on any reported error.

## Numbers and currencies

`common/utils.ts` holds every number formatter, each cached by its locale and
options. Each takes the locale first; a component reaches them bound to the
interface's current one through `useFormat()` (`src/i18n/format.ts`), which
renders it again when the language changes:

| Function | `pt-BR` | `en-US` |
| --- | --- | --- |
| `formatMoney('1234.56', 'BRL')` | `R$ 1.234,56` | `R$1,234.56` |
| `formatMoney('1234.56', 'USD' \| 'EUR')` | `US$ 1.234,56`, `€ 1.234,56` | `$1,234.56`, `€1,234.56` |
| `formatMoney('-1234.56', 'BRL')` | `-R$ 1.234,56` | `-R$1,234.56` |
| `formatCompactMoney(1234, 'BRL')` | `R$ 1,2 mil` (axis ticks) | `R$1.2K` |
| `formatPrice('0.123456', 'USD')` | `US$ 0,123456` | `$0.123456` |
| `formatUnitAmount('0.00001234', 'BRL')` | `R$ 0,00001234` | `R$0.00001234` |
| `formatQuantity('1234.5678')` | `1.234,5678` | `1,234.5678` |
| `formatPercent('0.1234')` | `12,34%` | `12.34%` |
| `formatList(['a', 'b', 'c'])` | `a, b e c` | `a, b, and c` |
| `currencyNameOf`, `currencySymbolOf` | `Real brasileiro`, `R$` | `Brazilian Real`, `R$` |

In `pt-BR`, `Intl` puts a no-break space (U+00A0) between the symbol and the
figures.

* **Formatting only.** Formatters take the API's decimal strings, which
  `Intl.NumberFormat` formats exactly. No calculation changed: `lib/decimal.ts`
  still counts in `bigint` units.
* **Currencies.** A new record defaults to `DEFAULT_CURRENCY` (`BRL`) in
  every language. Every record keeps and shows its own currency, with that
  currency's minor units (`JP¥ 1.235`, `¥1,235`). Totals in different
  currencies are listed side by side, never added, and nothing is converted.
  A switch changes how an amount is written, never the amount or its
  currency.

## Typed numbers

Money fields take digits only, entered from the right, so typing never meets
a separator. A pasted amount and the free-text quantity field go through
`readDecimal`. It accepts both conventions, with the interface's language as
the reference:

* The language's decimal separator (`,` in `pt-BR`, `.` in `en-US`) always
  separates the decimals: in `pt-BR`, `1,5` → 1.5 and `1,500` → 1.5.
* With both separators, the last one separates the decimals: `1.234,56` and
  `1,234.56` → 1234.56.
* Repeated separators between groups of three digits are a grouped whole
  number: `1.234.567`.
* The group separator alone before exactly three digits is ambiguous, because
  `1.500` is 1500 in Brazil and 1.5 in the US. The field refuses it and names
  both readings: "escreva 1,500 se houver casas decimais ou 1500 se for um
  número inteiro". In `en-US` the same holds for `1,500`.
* The other separator anywhere else separates the decimals: `1.5` → 1.5.

A field that shows a stored value writes it with `decimalInputTextOf` (`1,25`
in `pt-BR`, `1.25` in `en-US`, no grouping), which `readDecimal` reads back
unchanged. The bills list keeps its amount filters in the address as the API's
decimals, so a switch keeps them and writes them in the new convention. Text
typed into a form before a switch stays as typed; it is read in either
convention, except the ambiguous case above.

## Dates and time zones

`lib/dates.ts` holds every date formatter, each taking the locale first and
reached through `useFormat()` like the number formatters:

| Value | `pt-BR` | `en-US` | Zone |
| --- | --- | --- | --- |
| Calendar day (`YYYY-MM-DD`): due dates, payments | `28/10/2026` | `10/28/2026` | written at its UTC midnight and read in UTC, so no offset moves it |
| Month | `out. de 2026`, `outubro de 2026`, `out.` | `Oct 2026`, `October 2026`, `Oct` | UTC |
| Day with weekday | `qua., 28 de out.`, `quarta-feira, 28 de outubro de 2026` | `Wed, Oct 28`, `Wednesday, October 28, 2026` | UTC |
| Performance series day | `28/10/2026` | `10/28/2026` | UTC |
| Transaction execution, quote time | `28/10/2026`, `28/10, 14:30` | `10/28/2026`, `10/28, 02:30 PM` | the browser's zone, the one the instant was recorded in |
| Weekday names | `dom.` … `sáb.`, `domingo` … `sábado`, `D S T Q Q S S` | `Sun` … `Sat`, `Sunday` … `Saturday`, `S M T W T F S` | — |

The date picker (`components/ui/calendar.tsx`) takes the matching
`react-day-picker` locale, so its month and weekday names switch too.

An invalid day such as `2026-02-30` formats as nothing, never as a shifted
date. A day picked for a transaction is recorded by `instantOfCalendarDay` as
the later of its local and UTC midnights, so both readings name the same day.
`APP_TIME_ZONE` applies only to a date a message formats itself: the API
messages ending in a day, which pass it as a UTC date to
`{date, date, ::ddMMyyyy}`.

## Error messages

`lib/api-error-message.ts` turns a failed request into a sentence. It never
shows the API's text, the transport's text or a stack.

1. Timeout and network failures have their own messages. A 429 says when to
   retry, from `Retry-After`: "Tente novamente em 2 minutos".
2. A known API message maps to its own key. The table mirrors the messages in
   the API's `config/Constants.ts`. Messages built from the web's limits
   ("at most 24 months") and messages ending in a day ("… (2026-10-28)") are
   matched by pattern and rewritten in the interface's language, with the day
   as `28/10/2026` or `10/28/2026`.
3. An unknown message falls back to its category (`code`), then to the status
   code. Anything else gets `errors.unexpected`, or a caller's own wording such
   as "Não foi possível salvar a conta.".

`presentSubmitError` places each field the API refused under that field, with
the field's own message or `Valor inválido`. An API message added without a
table entry still reads as its category. Add the entry when adding the
message.

## Tests

backend. It also runs in CI and in `docker compose run --rm web-check`.
Components render with `renderToStaticMarkup` inside the app's provider
(`src/test/intl.tsx`), in `pt-BR` unless a test passes another locale. The web
has no DOM test library, so what a switch does over time is tested on
`runLocaleSwitch` directly, and what the tree renders is tested per locale. A
component that reads a query renders over a `QueryClient` seeded with the
response (`withQueryData`): a static render runs no effect, so it fetches
nothing and shows what the cache holds. A click, the switcher's choice or the

## Adding a locale

Only a complete catalog is offered: a locale in `LOCALES` without one does not
compile.

1. Add the tag to `LOCALES`, and its names to `LOCALE_NAMES` and
   `LOCALE_SHORT_NAMES`, in `src/i18n/config.ts`, each written in the
   language itself.
2. Copy `messages/en-US/` to `messages/<tag>/`, translate the values, and
   register the catalog in `MESSAGES` (`messages/index.ts`) and
   `CATALOG_LOADERS` (`messages/load.ts`). `LocaleMessages` makes the compiler
   refuse a missing or extra key. The catalog test also refuses a message
   whose ICU arguments differ from the reference's.
3. Write each plural for the language's CLDR categories, and keep `=0` where a
   count can be zero.
4. Add the `react-day-picker` locale to `DAY_PICKER_LOCALES` in
   `components/ui/calendar.tsx`.
5. Both selectors list the new locale with no further change, and the
   formatters take it as they take the others.
6. `DEFAULT_CURRENCY` is not tied to the locale. Records keep their currency
   whatever the language.
7. The API mapping needs no change: its table maps to keys, which every
   catalog has.

## Known limitations

* Errors are matched by the API's English message, because the API sends no
  reason code beyond the category. A reworded API message falls back to its
  category until the table follows.
* A history field the web does not know is labeled by the API's own field
  name.
* The preference belongs to the browser, not to the account: it is a cookie,
  kept after signing out, and another device starts in `pt-BR`. Moving it to
  the profile would need an API field.
* Another open tab keeps its language until it loads a page again.
* A toast already on screen, and an error the server set on a form field,
  stay in the language they were written in until they are replaced.
* A switch downloads the new catalog twice: once as its chunk, so the
  interface changes at once, and again in the refreshed server payload.
